# Session Actions

Temporary, repository-related development and test sessions executed on GitHub-hosted runners through the approved Workflow MCP action protocol.

Implementation is tracked by [Spec #1](https://github.com/lirtual/session-actions/issues/1). GitHub workflow discovery is not execution authorization; no session should be dispatched without a published and approved Workflow MCP plan.

## Native Task acceptance

`.github/workflows/verify-action.yml` is a minimal **Task** for validating the approved Workflow MCP lifecycle (not a persistent Session or general-purpose shell). It declares all three required server-owned identity inputs; only the bounded `outcome` choice is caller-selectable.

Before an owner-approved live acceptance, the repository owner must configure these **non-secret Actions variables** with the already-approved Workflow MCP endpoint and audience:

- `WORKFLOW_ACTION_CLAIM_URL` — the HTTPS Worker origin ending in `/github/action/claim`
- `WORKFLOW_ACTION_OIDC_AUDIENCE` — exactly the server's `GITHUB_ACTION_OIDC_AUDIENCE`

The action retries only temporary signed Claim HTTP 503 responses with fresh OIDC tokens, accepts a signed `already_claimed` replay after a lost HTTP receipt, and permanently rejects HTTP 403. It fails closed if either variable, a valid GitHub-issued OIDC token, or the D1 Attempt claim is unavailable. It never reads application secrets or joins Tailscale.

Live `workflow_dispatch` requires the workflow definition on GitHub's **default branch** and an owner-reviewed, SHA-bound Git tag. An approved Task on protected `v0.1.1` actually completed [GitHub Run #40056368526](https://github.com/lirtual/session-actions/actions/runs/40056368526) with signed Claim and successful Workflow MCP terminal reconciliation; CI alone would not prove this.

## Five native Session Actions

Each workflow lives in its own file and uses GitHub OIDC → Workflow MCP Claim → access setup → verified Ready → bounded hold → cleanup. Only the ubuntu and windows Sessions join the private Tailnet. The web Sessions use Cloudflare Quick Tunnels without a Tailscale dependency: chrome and code-server require Cloudflare email OTP, while openlist is public at the Tunnel layer and uses its own login and guest permissions:

| Workflow | GitHub-hosted runner | Private access | Local service |
| --- | --- | --- | --- |
| `ubuntu.yml` | Ubuntu | Password SSH as the existing `runner` account, bound to Tailscale IPv4 | Minimal command-line development |
| `windows.yml` | Windows | SSH and RDP as the existing Runner administrator, over private Tailscale | PowerShell, files and remote desktop (live RDP acceptance pending) |
| `chrome.yml` | Ubuntu | Email-OTP protected Quick Tunnel HTTPS | chrome GUI bound to `127.0.0.1:3000`; no separate login |
| `code-server.yml` | Ubuntu | Email-OTP protected Quick Tunnel HTTPS | code-server `4.140.0`, `--auth none`, bound to `127.0.0.1:8080` |
| `openlist.yml` | Ubuntu | Cloudflare Quick Tunnel HTTPS | openlist Docker `v4.2.6` with native `admin` password on `127.0.0.1:5244` |

**How to find your Session:** For ubuntu and windows, the default `session_mode: temporary` gives each Run an independent `sa-<github_run_id>-a<github_run_attempt>` Tailnet hostname. Select `session_mode: fixed` to request exactly `session-ubuntu` or `session-windows`. Workflow MCP atomically limits each fixed Action to one active physical Session (starting, ready, stopping and uncertain all count) within the existing four global slots. A second fixed start does not dispatch another GitHub Job: the failed start provides the existing Session Run ID for lookup. Only verified physical termination releases the fixed slot. Tailscale's existing GitHub Action Post step logs out its ephemeral node when the Job finishes; if an old device has not released its name and Tailscale allocates a suffixed name, startup fails before Ready rather than exposing a misleading locator. After the signed Ready state, `workflow_status` exposes `private_hostname` (for example `sa-123456789-a1`) and still reports `physical_health: unverified` until physical state reconciliation. These names work only within an authorized tailnet with correct MagicDNS/Tailscale SSH access rules. For ubuntu use `ssh runner@<private_hostname>`; for windows use `ssh runneradmin@<private_hostname>` (the actual account is detected from each Runner). Both use the same SSH password from `SESSION_SYSTEM_PASSWORD`. Windows also supports RDP on Tailscale TCP/3389 using `runneradmin` and the same underlying Windows account password. The disposable GitHub-hosted Windows Runner enforces **only a minimum of 8 characters** for this local account password; no fixed uppercase/lowercase/number/symbol combination is required. This local policy adjustment is refused on self-hosted Runners, and the SSH/RDP network remains Tailnet-restricted. Windows SSH and RDP authenticate the same existing local account and automatically share `SESSION_SYSTEM_PASSWORD`; no RDP-specific Secret is needed. For chrome, code-server and openlist, the signed Ready request records a temporary HTTPS URL on `trycloudflare.com`, exposed as `session_url` through existing Workflow MCP `workflow_status` / `workflow_result` only while the Session is Ready. GitHub Job Summary and the one-day `session-tunnel-url` artifact remain fallbacks. For chrome and code-server, the email one-time PIN is the **only** login gate; the services listen on loopback only and cannot be exposed unless the protected Tunnel's anonymous redirect is verified. openlist still requires its native administrator login to preserve its database-backed privileges. The temporary `trycloudflare.com` URL is a public Internet endpoint without an availability guarantee. chrome and code-server require Cloudflare email OTP before access; openlist allows anonymous HTTP requests and enforces its own user and guest permissions.

**Supply-chain bounds:** the code-server 4.140.0 linux-amd64 download is checked against hardcoded SHA-256 `864c5d01c808ade57e4d12c708717be7a187219fded60428f263b9e2da9f6b48` (matched two distinct GitHub-hosted Runner downloads). openlist v4.2.6 is pinned to multi-architecture image index digest `sha256:c555c6e1c8af2aead38ed12ec761ac077fdf046d19cf033414be8e056aec6b64`. Any new release must be reviewed and update these immutable values explicitly; the version/tag alone is not authority.

The three internal workflow_dispatch inputs `attempt_id`, `dispatch_id`, `capability_id` are supplied **only** by Workflow MCP. Users may choose `duration_minutes` (1–330, default 330). These workflows do not accept shell commands or arbitrary URLs as input.

**Repository configuration before any separately approved live acceptance:**

- Actions variables: `WORKFLOW_ACTION_CLAIM_URL` (HTTPS, exactly ending `/github/action/claim`) and `WORKFLOW_ACTION_OIDC_AUDIENCE` (exact server-owned Action OIDC audience).
- Actions variables: `TS_OAUTH_CLIENT_ID` (Tailscale workload identity client ID), `TS_AUDIENCE` (Tailscale OIDC federation audience). These are non-secret identifiers; Tailscale identity binding and tag authorization are enforced by the Tailnet trust policy.
- GitHub Actions **Variable**: `SESSION_TUNNEL_ALLOWED_EMAIL` must be exactly one mailbox that you can receive email at. The chrome and code-server workflows fail closed if it is missing or invalid; openlist does not use this variable. Set it under repository Settings → Secrets and variables → Actions → Variables; do not add a wildcard email domain. This is an **additional login gate**, not an extra service password.
- Actions secrets: `SESSION_SYSTEM_PASSWORD` (windows and ubuntu SSH), `SESSION_SERVICE_PASSWORD` (openlist administrator login only), and `OPENLIST_DATABASE_URI` (Aiven-compatible MySQL connection URI), and `OPENLIST_DATABASE_CA` (Aiven project CA certificate PEM or rotation bundle; required for verified TLS). Values must be non-empty, single-line and accepted by their application or OS. Do not paste passwords into Workflow YAML or logs. Retire `SESSION_SSH_PUBLIC_KEY`, `SESSION_SSH_PASSWORD`, `SESSION_RDP_PASSWORD`, intermediate `WINDOWS_ADMIN_PASSWORD` and obsolete `OPENLIST_ADMIN_PASSWORD` only after approved rollout.
- Tailnet: configure a narrowly scoped `tag:session-actions`, an appropriate GitHub workload identity trust policy and ACL grants. The windows and ubuntu Sessions use ordinary OpenSSH restricted to Tailnet TCP/22 and therefore rely on Tailscale **network grants**; Windows RDP on TCP/3389 is likewise restricted to Tailnet access. chrome, code-server and openlist use HTTPS Cloudflare Quick Tunnels, **not** Tailscale SSH, and must not be considered Tailnet-private. The tag does not itself grant access to unrelated nodes.
- Workflow MCP: the signed Claim and Ready endpoints, GitHub Git ref/commit approval, physical Run identity, D1 migrations, four active slots, expiry monitoring and cancellation must be deployed and verified separately.

**openlist external MySQL URI and CA:** Configure both `OPENLIST_DATABASE_URI` and `OPENLIST_DATABASE_CA` as GitHub Actions **Secrets**. Use `mysql://USER:PASSWORD@HOST:PORT/DATABASE?ssl-mode=REQUIRED` (percent-encode reserved characters in credentials). The database name is taken from the URI path; use a dedicated MySQL database/account with the intended table prefix `x_`. The parser accepts `REQUIRED` and `VERIFY_IDENTITY` and **strengthens both to verified TLS** by configuring the Go MySQL driver with `tls=true` and the supplied Aiven CA bundle via `SSL_CERT_FILE`, which validates the server certificate and hostname. Missing or malformed PEM, unencrypted modes, and unknown query options fail closed; there is **no** `skip-verify` or SQLite fallback. Aiven's CA may rotate: update the Secret with the current/new CA bundle before rotation completes. Never include a real MySQL URI or CA private key in source, logs, or PR discussions. Connecting a new openlist version can alter existing external MySQL tables. Before openlist initialization, the existing GitHub Runner's MySQL client performs **read-only** `information_schema` checks over verified TLS: the target URI database must exist, contain no unrelated table/view names, and an existing `x_` namespace must contain the core `x_users`, `x_storages`, and `x_setting_items` tables (not views). A partial or mismatched schema fails closed before migrations or admin-password changes. This guard does **not** independently prove database ownership or that the corrected Secret points to the intended schema. No additional Database MCP connection, tool or service is required. The owner waived a separate backup prerequisite on 2026-10-24; the waiver does not authorize modifications to unexpected existing data.

The signed **Claim runs before** the pinned Tailscale Action, SSH authorization, service secrets and `ready`. An unregistered direct `workflow_dispatch` must stop at Claim; its GitHub Job failure is an expected security result, not proof that the private Session was started. The Tailscale federation needs a client ID, audience, `auth_keys` scope limited to `tag:session-actions`, and an explicit GitHub OIDC trust policy; Tailscale's own [workload identity guide](https://tailscale.com/docs/features/workload-identity-federation) describes the required identity exchange. Do not grant `tag:session-actions` access to unrelated nodes.

The three web services bind only to loopback and use SHA-256-pinned `cloudflared 2026.10.3` Quick Tunnels. chrome and code-server require `--allowed-mail` with the `SESSION_TUNNEL_ALLOWED_EMAIL` mailbox and fail closed without it; an anonymous `GET -> 302` email-OTP redirect is required for Ready, and an unauthenticated `POST -> 401` must also be checked in CI. They have no second application password. openlist deliberately omits `--allowed-mail`: anyone with its temporary public URL can reach its public pages, guest routes and shares, subject to native OpenList permissions. Its Tunnel is Ready only when an anonymous request to `/api/public/settings` returns the expected OpenList JSON; the startup separately verifies its administrator login before Ready. Do not mistake these checks for proof that private OpenList data are protected: review guest permissions, public shares and admin credentials before live activation. Final positive access acceptance requires real OTP login and usable GUI for chrome/code-server, or actual anonymous/public-page and native-admin-login checks for openlist, with stable access for at least 60 seconds. [cloudflare/cloudflared#1752](https://github.com/cloudflare/cloudflared/issues/1752) reports that some protected Quick Tunnel sessions expire within seconds; if reproduced, do not remove `--allowed-mail` from chrome/code-server as a workaround. **Cloudflare describes Quick Tunnels as development/testing only**; they offer no production SLA. No named Tunnel, static public hostname or Tunnel Token is required.

Windows uses the existing GitHub-hosted Runner administrator account with SSH plus native RDP, while Ubuntu Linux uses its existing unprivileged Runner account (which has passwordless sudo access). Each SSH listener binds only to its Tailnet IPv4 address; Windows also restricts SSH/RDP inbound firewall rules to that adapter/address and requires RDP NLA. There is no new user or SSH authorized key for either. Passwords are accepted according to the platform's own local account policy, without a custom 16-character minimum. Because these accounts can perform privileged operations, tightly restrict Tailnet network access and protect the shared GitHub Actions Secret. Windows administrator password-authenticated SSH and RDP have now both been confirmed by the owner on real Windows-hosted Runners (latest SSH [#40109374696](https://github.com/lirtual/session-actions/actions/runs/40109374696)); authentication tests do not by themselves prove any later Session is still online. The openlist container uses ephemeral Runner-local configuration and cache while its **external MySQL database persists** beyond Session termination. Inspect database ownership and schema read-only before the first live openlist initialization. The owner waived a separate manual backup prerequisite on 2026-10-24; do not initialize or reset unexpected existing data. Runner cleanup never drops database tables. chrome and code-server temporary Runner state is discarded when the Job ends. This is not a backup service or permanent remote computer.

The Session duration is bounded to 330 minutes by the first Runner step (before checkout), while the GitHub Job uses `timeout-minutes: 360` as a separate hard safety cutoff, leaving approximately 30 minutes for best-effort shutdown and cleanup. The first step is the earliest controllable time marker, not GitHub's internal pre-step scheduling timestamp. The shared stdlib-only Python helper validates and preserves that marker; it never restarts the clock. If the Job fails before Ready, the published Workflow must not claim a successful Session. Ready means the private service passed its local health check; it is not a guarantee that the requesting device can connect through Tailnet ACLs.

### Acceptance and publication gate

The five independent Sessions have been exercised through **published and approved** Workflow MCP plans and actual GitHub-hosted runners. ubuntu [#40057129644](https://github.com/lirtual/session-actions/actions/runs/40057129644) completed signed Claim/Ready, **the previous Tailscale SSH authentication**, command execution, cancellation and quota release. That prior run does **not** validate the new password-authenticated OpenSSH implementation. chrome [#40057287818](https://github.com/lirtual/session-actions/actions/runs/40057287818), code-server [#40057289722](https://github.com/lirtual/session-actions/actions/runs/40057289722) and openlist [#40057291691](https://github.com/lirtual/session-actions/actions/runs/40057291691) previously returned signed Ready using SSH port forwarding and loopback HTTP responses; **those runs do not validate the new Tunnel/native-password access path**, which requires its own acceptance. A four-Session concurrency test denied a fifth attempt without dispatch. Windows [#40060922399](https://github.com/lirtual/session-actions/actions/runs/40060922399) on protected `v0.1.13` passed OIDC Claim, Tailnet and **the previous non-admin ED25519 SSH scheme** (`WIN_FINAL_PASS`, exit 0), then physically terminated and released its slot. This historic evidence does **not** validate the new administrator password-login scheme, which requires separate live approval and access testing. In each case, signed Ready was correctly distinguished from external Job completion.

PR CI checks Actionlint, shared protocol and OIDC Claim failure tests, native Windows prerequisites and actual loopback-bound chrome, code-server and openlist service startup. openlist's local startup now additionally requires a successful admin login with the configured ephemeral password **before** signed Ready; the CI smoke uses only a temporary CI password. A prior live openlist Session on protected `v0.1.14` [#40062276499](https://github.com/lirtual/session-actions/actions/runs/40062276499) confirmed the startup script's `openlist admin login validated` message, signed Ready, authenticated Tailscale SSH access and HTTP 200; normal cancellation reconciled to physical `cancelled`, external `terminated`, and 0 active slots. The `v0.1.14` evidence here is historical. Current reviewed published versions use `v0.1.21` for chrome/code-server, `v0.1.20` for Windows, and `v0.1.19` for ubuntu/openlist; current physical health must be checked per Run. A separate one-minute **natural-expiration** Linux Session [#40062561451](https://github.com/lirtual/session-actions/actions/runs/40062561451) finished its own bounded hold and GitHub Job with `success` (not user cancellation), then the Worker reconciled the external Session to `terminated` / Attempt `succeeded` and restored the active slot count to zero. Broader negative/fault-injection cases are covered in `lirtual/mcp-workers/apps/workflow-mcp-worker/tests/github-action-{oidc,session,orchestration,review,inputs,run-state}.test.ts`, including wrong identities and Git refs, duplicated/lost callbacks, uncertain GitHub responses and no premature quota release. Those are **automated tests**, not live adversarial production experiments. A continuous 330-minute wall-clock run has not been executed; the workflow's 360-minute hard limit, 330-minute duration input bounds and short-lived expiration behavior are distinct controls.

Release and acceptance are separate gates. Keep production D1 changes owner-executed, and never bypass the Worker release check for an unresolved or indeterminate Run. Before activating a Session, configure the approved GitHub identity and required credentials. ubuntu and windows additionally require the narrow Tailscale tag/SSH policy. Web Sessions use Quick Tunnels: chrome/code-server require Cloudflare email OTP as their sole login, while openlist uses a public Tunnel with native login/guest permissions. Never expose local origins directly or disable the chrome/code-server OTP gate as a workaround.


**Action naming and release boundary:** The Session Action identifiers are `ubuntu`, `windows`, `chrome`, `code-server` and `openlist`. The former `linux.yml` / `linux-ssh.sh` names are retired. Renaming a GitHub Workflow changes its GitHub workflow identity: existing published Workflow MCP plans pinned to the retired file/Workflow ID are **not automatically migrated**. Before executing the renamed `ubuntu` Action, release an owner-reviewed immutable Git tag containing `ubuntu.yml`, check the newly discovered workflow ID and contract, and explicitly publish a new approved Workflow MCP plan. Do not reuse the previous `linux.yml` approval or assume the old published Workflow remains dispatchable.

## Production acceptance boundaries

- Web Session access deliberately differs from the original Tailnet-only Spec: Quick Tunnel creates ephemeral public HTTPS endpoints. chrome/code-server are gated by Cloudflare email OTP and have **no second password**; openlist has no Cloudflare OTP and instead enforces native accounts/guest permissions for persistent data. OTP redirect and POST rejection are security prechecks for chrome/code-server, **not** proof of successful authenticated access. Do not claim positive acceptance without a real owner OTP login and GUI for chrome/code-server, or public route plus native OpenList admin-login checks.
- A signed Ready records the temporary Quick Tunnel locator on the existing D1 Session row. Existing `workflow_status` and `workflow_result` expose `session_url` only while Ready; the URL is hidden when stopping/terminated and discarded on verified physical release. This is a connection hint, not proof of successful Cloudflare OTP or application login.
- openlist uses the configured external MySQL schema and **does persist database records after a Session ends**. Its preflight checks table shape only, not ownership or an untouched dataset; the owner must confirm the intended schema and acceptable retained test data. The Runner cleanup removes local files, not the external database. Never automatically drop or overwrite the external schema as part of Session cleanup.
- Windows live password-authenticated RDP and SSH have now both been accepted by the owner; the GitHub-hosted Runner's minimum-8-character policy remains scoped to disposable Windows Runners. Future Runs must still pass actual setup, signed Ready, and physical cleanup checks; OIDC Claim/Tailscale alone is not proof of access.
- The existing CI now runs for relevant default-branch changes as well as pull requests. A passing isolated CI does not replace authorized full production access acceptance.
