# GitHub Actions

Reviewed Task and temporary Session execution on GitHub-hosted runners through the existing Workflow MCP action protocol.

Repository identity migration is tracked by [Spec #607](https://github.com/lirtual/mcp-workers/issues/607). The repository name changes, but the original Repository ID, Task/Session workflows, tags and historical evidence must remain intact. Local `session-actions` paths and the Tailscale tag are intentionally unchanged.

Implementation is tracked by [Spec #1](https://github.com/lirtual/github-actions/issues/1). GitHub workflow discovery is not execution authorization; no session should be dispatched without a published and approved Workflow MCP plan.

## Native Task acceptance

`.github/workflows/verify-action.yml` is a minimal **Task** for validating the approved Workflow MCP lifecycle (not a persistent Session or general-purpose shell). It declares all three required server-owned identity inputs; only the bounded `outcome` choice is caller-selectable.
The verification Task can optionally set `emit_artifact: true` on a newly
reviewed immutable Tag. Only after its signed Claim and successful work it
uploads one static, public-safe `workflow-verified.json` GitHub Artifact
(`workflow-verified`, one-day retention). The default is `false`, preserving
existing Task cost, output and failure behavior; no OIDC token, Attempt ID,
Session data or download credential is included. This Artifact is fetched only
as owner-authorized, provenance-checked metadata through Workflow MCP
`workflow_result`, not stored in D1 or published as a download URL.

Before an owner-approved live acceptance, configure the non-secret Actions variable `WORKFLOW_ACTION_CLAIM_URL` with the approved HTTPS Workflow Worker endpoint ending in `/github/action/claim`. The Runner first calls `GET /github/action/config` on the same trusted origin to obtain the Worker's current Action OIDC Audience (bounded response, no redirects, no fallback), before requesting a GitHub OIDC token. The Repository variable `WORKFLOW_ACTION_OIDC_AUDIENCE` is no longer read. This requires the separately published Workflow Worker to support the discovery endpoint **before** activating this Runner revision.

The action retries only temporary signed Claim HTTP 503 responses with fresh OIDC tokens, accepts a signed `already_claimed` replay after a lost HTTP receipt, and permanently rejects HTTP 403. It fails closed if either variable, a valid GitHub-issued OIDC token, or the D1 Attempt claim is unavailable. It never reads application secrets or joins Tailscale.

Live `workflow_dispatch` requires the workflow definition on GitHub's **default branch** and an owner-reviewed, SHA-bound Git tag. An approved Task on protected `v0.1.1` actually completed [GitHub Run #40056368526](https://github.com/lirtual/github-actions/actions/runs/40056368526) with signed Claim and successful Workflow MCP terminal reconciliation; CI alone would not prove this.

## Download Task (Spec #51)

The bounded `.github/workflows/download.yml` Task uses aria2 and one Owner-approved rclone Remote for repository-related public HTTP(S) artifacts. As of 2026-11-06, the authenticated manual-only production `download` Workflow is **active** (Published Version `465a8021-168a-4b4b-9b70-7cf2e06c8bbd`); it has no Cron/Webhook trigger and dispatches at most one physical GitHub Task per Run. The batch may contain multiple approved source URLs. A successful download is followed by a **separate** `notify_bark` step; notification acceptance is not proof of delivery or cloud-file integrity.

The current published Plan uses the approved `refs/heads/main` exception, **not** the historic immutable `v0.1.42-rc.9` Tag. Each admitted Run must independently verify its resolved GitHub commit and successful CI; discovery and CI alone do not authorize dispatch. The Task must pass its Workflow MCP OIDC Claim before validating the batch or accessing download credentials. Before any future Draft publication, recheck its declared SHA/ref against the current main and validate the exact revision.

The current `main` workflow reads these settings from GitHub Actions **repository-level** Variables and Secrets. The `download` Environment remains attached to the job for its existing OIDC identity context but has **no** Environment Variables or Secrets:

- **Variable `DOWNLOAD_REMOTE_PATH`** (currently `koofr:Downloads`): fixed Owner-approved rclone Remote plus an existing, case-sensitive relative destination root. Missing, unsafe, differently cased or nonexistent roots fail closed.
- **Secret `DOWNLOAD_RCLONE_CONFIG`**: original multiline `rclone.conf`, **not Base64**. Only the post-Claim execution step references the Secret. The Runner writes it to a private, temporary `0600` file for the isolated uploader and removes it on exit; never print, commit or expose its value.

The JSON batch retains a `remote` field that must match the approved Remote, with no caller-controlled cloud root or command. A URL-only batch uploads directly to `koofr:Downloads/<downloaded-filename>`; optional validated relative `destination_dir` adds subdirectories. The Runner uses an isolated temporary Task directory, but **no random per-Task directory is added remotely**. Before any cloud write, the full batch is checked for path conflicts and case aliases, pre-existing targets are rejected, and rclone uses `--immutable`. Each uploaded file is independently read back and SHA-256 verified. This is **not** a Koofr server-atomic create-only guarantee: external concurrent writers can still race. Partial or unknown writes are non-success, never blindly replayed or deleted.

**Current production E2E:** [GitHub Run #42157095347](https://github.com/lirtual/github-actions/actions/runs/42157095347) ran once on `main` SHA `7826ba065de7a6ea1088196d3ee6950bf9738bd6` and completed successfully (2026-11-06). The single-file target `Downloads/e2e-20261106-main-v2/README.md` had an independent Koofr readback of **32,547 bytes** and SHA-256 `8514bbdec5935a3844ecf80e2a2487c58c1460a6d270a74895953d2814b6e5ee`; the Workflow Run `fb90ac23-f0ea-4ac9-b114-dc57877bfc0a` and `notify_bark` both succeeded, and the Owner confirmed receipt on iPhone. Earlier `rc.5` multiple-URL and `rc.7` direct-root tests remain historical evidence for their own revisions, not a substitute for the current `main` E2E.

**Accepted limits:** Q13 permits public HTTPS without a TLS/FQDN allowlist; Q15 retains non-atomic destination TOCTOU risk. Live mid-upload fault injection was **Waived / Not performed**, and a live duplicate-target negative dispatch is **Not performed** (local regression tests exist). The Q34 independently signed success receipt is **Optional / Not implemented**. No such unperformed test is counted as Pass.

## Optional Session RCA bootstrap (Spec #62 — candidate only)

The reviewed Windows/Ubuntu Sessions retain signed Ready, SSH/RDP, Hold and cleanup. After signed Ready an optional, bounded bootstrap may launch a **job-scoped foreground RCA Agent** using the existing authenticated Remote Control protocol; the workflow does not install or reconfigure any personal Agent, scheduled task or permanent device. Bootstrap failures cannot fail the underlying Session; `list_devices` and Workflow's live authorization (not bootstrap success) determine actual online availability.

The **candidate new workflow** attempts the optional RCA bootstrap by default after signed Ready, with no GitHub Variables for its Release version or digest. The bootstrap queries the fixed public GitHub Releases API for `lirtual/remote-control-agent`, paginates completely within bounded limits, and selects the highest non-Draft **complete** `vMAJOR.MINOR.PATCH` tag. GitHub releases marked prerelease are eligible if their tag is complete; tags containing `-rc` or any suffix are ineligible. The selected Release must be immutable, with a complete uploaded platform-specific asset and GitHub-provided SHA256 digest; the exact archive is hashed and independently checked before execution. No mutable-Release, API-failure, missing-asset or checksum fallback to an older version is allowed. GitHub Digest establishes consistency with published metadata, **not** that future released code has been separately reviewed; choosing automatic newest execution accepts that trade-off.

The bootstrap also checks GitHub-hosted Runner/Session identity, HTTPS transfer, bounded archive types/paths and bundle metadata before launching the job-private packaged Session entrypoint. The existing two-minute optional Step bound and `continue-on-error` preserve the main SSH/RDP Session on RCA failure. Existing published Git Tags **still use** `SESSION_RCA_RELEASE_TAG`, `SESSION_RCA_LINUX_X64_SHA256` and `SESSION_RCA_WINDOWS_X64_SHA256` until their Plans are explicitly republished. Each immutable Workflow Plan must still be reviewed and published against the approved new GitHub Actions Tag. **No production configuration changes or live Session E2E are claimed by this candidate PR.** On a SHA-reviewed Session workflow, signed Ready now sends the exact job-environment `DURATION_MINUTES` (1–300) to Workflow MCP, which freezes it once in the existing Session record. RCA admission for repository-mode Sessions is allowed only with that nonrenewable signed snapshot and the independently verified GitHub physical Job start; missing, altered or pre-migration snapshots deny RCA only. The Workflow database migration must be applied before the matching Worker code is activated. SSH/RDP continues to honor the repository variable unchanged.

## Five native Session Actions

Each workflow lives in its own file and uses GitHub OIDC → Workflow MCP Claim → access setup → verified Ready → bounded hold → cleanup. Only the ubuntu and windows Sessions join the private Tailnet. The web Sessions use Cloudflare Quick Tunnels without a Tailscale dependency: chrome and code-server require Cloudflare email OTP, while openlist is public at the Tunnel layer and uses its own login and guest permissions:

| Workflow | GitHub-hosted runner | Private access | Local service |
| --- | --- | --- | --- |
| `ubuntu.yml` | Ubuntu | Password SSH as the existing `runner` account, bound to Tailscale IPv4 | Minimal command-line development |
| `windows.yml` | Windows | SSH and RDP as the existing Runner administrator, over private Tailscale | PowerShell, files and remote desktop (live RDP acceptance pending) |
| `chrome.yml` | Ubuntu | Email-OTP protected Quick Tunnel HTTPS | chrome GUI bound to `127.0.0.1:3000`; no separate login |
| `code-server.yml` | Ubuntu | Email-OTP protected Quick Tunnel HTTPS | code-server `4.140.0`, `--auth none`, bound to `127.0.0.1:8080` |
| `openlist.yml` | Ubuntu | Cloudflare Quick Tunnel HTTPS | openlist Docker `v4.2.6` with native `admin` password on `127.0.0.1:5244` |

**How to find your Session:** For ubuntu and windows, the default `session_mode: fixed` requests exactly `session-ubuntu` or `session-windows`; both use GitHub-hosted `ubuntu-latest` / `windows-latest` runners. Explicitly select `session_mode: temporary` for an independent `sa-<github_run_id>-a<github_run_attempt>` Tailnet hostname. A fixed hostname is **not** a permanent VM: each fixed Session still has the same bounded lifetime and cleanup. Workflow MCP atomically limits each fixed Action to one active physical Session (starting, ready, stopping and uncertain all count) within the existing four global slots. A second fixed start does not dispatch another GitHub Job: the failed start provides the existing Session Run ID for lookup. Only verified physical termination releases the fixed slot. Tailscale's existing GitHub Action Post step logs out its ephemeral node when the Job finishes; if an old device has not released its name and Tailscale allocates a suffixed name, startup fails before Ready rather than exposing a misleading locator. After the signed Ready state, `workflow_status` exposes `private_hostname` (for example `sa-123456789-a1`) and still reports `physical_health: unverified` until physical state reconciliation. These names work only within an authorized tailnet with correct MagicDNS/Tailscale SSH access rules. For ubuntu use `ssh runner@<private_hostname>`; for windows use `ssh runneradmin@<private_hostname>` (the actual account is detected from each Runner). Both use the same SSH password from `SESSION_SYSTEM_PASSWORD`. Windows also supports RDP on Tailscale TCP/3389 using `runneradmin` and the same underlying Windows account password. The disposable GitHub-hosted Windows Runner enforces **only a minimum of 8 characters** for this local account password; no fixed uppercase/lowercase/number/symbol combination is required. This local policy adjustment is refused on self-hosted Runners, and the SSH/RDP network remains Tailnet-restricted. Windows SSH and RDP authenticate the same existing local account and automatically share `SESSION_SYSTEM_PASSWORD`; no RDP-specific Secret is needed. For chrome, code-server and openlist, the signed Ready request records a temporary HTTPS URL on `trycloudflare.com`, exposed as `session_url` through existing Workflow MCP `workflow_status` / `workflow_result` only while the Session is Ready. GitHub Job Summary and the one-day `session-tunnel-url` artifact remain fallbacks. For chrome and code-server, the email one-time PIN is the **only** login gate; the services listen on loopback only and cannot be exposed unless the protected Tunnel's anonymous redirect is verified. openlist still requires its native administrator login to preserve its database-backed privileges. The temporary `trycloudflare.com` URL is a public Internet endpoint without an availability guarantee. chrome and code-server require Cloudflare email OTP before access; openlist allows anonymous HTTP requests and enforces its own user and guest permissions.

**Windows RDP disconnect handoff:** The Runner uses the existing account-scoped `RemoteDisconnect` task to return its own disconnected RDP session to the console. The task is removed during cleanup; real RDP reconnect remains a separate live acceptance check.


**UU Lite retired (Spec #774):** New Windows Sessions use Tailscale, SSH, RDP and optional RCA only. The former UU installer, verification-code capture, signed Session Data reports and credential retrieval tool are not part of this source revision. Immutable historical Action Tags and Published Plans require a separately authorized production admission cutover.


**Supply-chain bounds:** the code-server 4.140.0 linux-amd64 download is checked against hardcoded SHA-256 `864c5d01c808ade57e4d12c708717be7a187219fded60428f263b9e2da9f6b48` (matched two distinct GitHub-hosted Runner downloads). openlist v4.2.6 is pinned to multi-architecture image index digest `sha256:c555c6e1c8af2aead38ed12ec761ac077fdf046d19cf033414be8e056aec6b64`. Any new release must be reviewed and update these immutable values explicitly; the version/tag alone is not authority.

The three internal workflow_dispatch inputs `attempt_id`, `dispatch_id`, `capability_id` are supplied **only** by Workflow MCP. Users may choose `duration_minutes` (1–300, default 300). These workflows do not accept shell commands or arbitrary URLs as input.

**Optional per-Run duration (preferred for newly published Workflow MCP plans):** All five Session Action YAMLs default to **300** minutes and the Runner strictly enforces **1–300** whole minutes. The Workflow engine can opt in once by declaring top-level `inputs.duration_minutes: 300` and setting the reviewed Action input to `duration_minutes: {ref: inputs.duration_minutes}` with `duration_mode: explicit`. Subsequent starts with no duration use 300, and starts with `workflow_run.inputs.duration_minutes` use the supplied 1–300 value **without republishing**. The exact reviewed GitHub tag and inputs other than duration remain immutable; the published Plan must explicitly opt in. Existing pinned `duration_mode: repository` workflows continue to work without changing their behavior until deliberately republished. The 360-minute job timeout is a separate emergency cleanup backstop, not the user-selectable Session maximum.

**Repository-managed formal Session duration:** Set the non-secret GitHub Actions repository variable `SESSION_DURATION_MINUTES` to `300` under **Settings → Secrets and variables → Actions → Variables**. Formal Published Workflow MCP Plans explicitly pin `duration_mode: repository` and a `duration_minutes: 300` fallback. Their *next* GitHub Jobs use the repository variable (1–300 whole minutes); changing the variable affects only new jobs, not active Sessions, and does not require republishing the formal Plan. If the variable is absent, these Plans use 300. If it is present but invalid or out of bounds, the first Runner step fails before Claim and service/Tailnet startup; it does not silently fall back or extend the lifetime. Tests and one-off approved Plans use the default `duration_mode: explicit` and their pinned `duration_minutes`, ignoring the repository variable. The source ref and choice of mode remain pinned by the reviewed Published Plan; a mutable repository variable only controls the bounded runtime duration of a new opted-in Session. GitHub Job `timeout-minutes: 360` and the 300-minute hard maximum still apply.

**Repository configuration before any separately approved live acceptance:**

- Actions variable: `WORKFLOW_ACTION_CLAIM_URL` (HTTPS, exactly ending `/github/action/claim`); Audience is fetched at runtime via the same-origin `GET /github/action/config` and remains validated server-side.
- Actions variable: `TS_OAUTH_CLIENT_ID` (Tailscale workload identity client ID). The new Windows/Ubuntu workflows derive the Audience as `api.tailscale.com/<client ID>`; this was compared against the full existing `TS_AUDIENCE` value on 2026-11-05 and found equal. Existing pinned Plans still read `TS_AUDIENCE` until republished. Tailnet trust policy, identity binding and tag authorization remain unchanged.
- GitHub Actions **Repository Variable**: `OWNER_EMAIL` must contain **exactly one explicit email address** (for example, `alice@example.com`). chrome/code-server reject missing or empty values, comma-separated lists, whitespace (including surrounding spaces and line breaks), wildcards and malformed local/domain parts **before downloading or starting the Tunnel**. There is no trimming, first-address selection, fallback or extra application password. openlist does not use this variable. Before activating the stricter validator, confirm the current Variable is a valid single mailbox; if not, have the Owner explicitly identify which one to retain and separately authorize the production configuration update. Audit actually executable Published Plans instead of inferring adoption from their stored SHA.
- Actions secrets: `SESSION_SYSTEM_PASSWORD` (windows and ubuntu SSH), `SESSION_SERVICE_PASSWORD` (openlist administrator login only), and `OPENLIST_DATABASE_URI` (Aiven-compatible MySQL connection URI), and `OPENLIST_DATABASE_CA` (Aiven project CA certificate PEM or rotation bundle; required for verified TLS). Values must be non-empty, single-line and accepted by their application or OS. Do not paste passwords into Workflow YAML or logs. Retire `SESSION_SSH_PUBLIC_KEY`, `SESSION_SSH_PASSWORD`, `SESSION_RDP_PASSWORD`, intermediate `WINDOWS_ADMIN_PASSWORD` and obsolete `OPENLIST_ADMIN_PASSWORD` only after approved rollout.
**Optional CLI credentials for interactive Ubuntu/Windows Sessions (Spec #93):** In the actual execution repository \`autoactions/github-actions\`, set repository Secrets \`GH_TOKEN\` (the interactive GitHub PAT) and \`CLOUDFLARE_API_TOKEN\`. Non-secret repository Variables \`GIT_USER_NAME\`, \`GIT_USER_EMAIL\`, and optionally \`CLOUDFLARE_ACCOUNT_ID\` configure the default Git author/committer and Cloudflare account; local repository Git identity still overrides the defaults. The custom PAT is distinct from Actions' built-in \`GITHUB_TOKEN\`. Only after signed Claim, disposable Ubuntu SSH Bash and Windows SSH/RDP PowerShell terminal profiles load the private Session token files; \`gh\` and Git HTTPS share \`GH_TOKEN\` through \`gh auth setup-git\`, while \`cf\` uses the Cloudflare API Token. \`cf\` is pinned to \`1.0.0-beta.14\` and installed opportunistically before any Token is supplied; setup failure or missing/expired Token does not block existing SSH/RDP readiness. Windows SSH switches to PowerShell on the hosted Runner; fresh SSH, remote-command and RDP entry points require separately approved real Session acceptance. No CLI credentials are injected into web Sessions, Download or CI. These tokens grant their own provider permissions, including possible production writes: Owner production authorization is still required. Tokens copied out of a Session are **not revoked** by Runner cleanup. Provisioning/rotating repository settings and live Session dispatch are separate authorization steps.

- Tailnet: configure a narrowly scoped `tag:session-actions`, an appropriate GitHub workload identity trust policy and ACL grants. The windows and ubuntu Sessions use ordinary OpenSSH restricted to Tailnet TCP/22 and therefore rely on Tailscale **network grants**; Windows RDP on TCP/3389 is likewise restricted to Tailnet access. chrome, code-server and openlist use HTTPS Cloudflare Quick Tunnels, **not** Tailscale SSH, and must not be considered Tailnet-private. The tag does not itself grant access to unrelated nodes.
- Workflow MCP: the signed Claim and Ready endpoints, GitHub Git ref/commit approval, physical Run identity, D1 migrations, four active slots, expiry monitoring and cancellation must be deployed and verified separately.

**openlist external MySQL URI and CA:** Configure both `OPENLIST_DATABASE_URI` and `OPENLIST_DATABASE_CA` as GitHub Actions **Secrets**. Use `mysql://USER:PASSWORD@HOST:PORT/DATABASE?ssl-mode=REQUIRED` (percent-encode reserved characters in credentials). The database name is taken from the URI path; use a dedicated MySQL database/account with the intended table prefix `x_`. The parser accepts `REQUIRED` and `VERIFY_IDENTITY` and **strengthens both to verified TLS** by configuring the Go MySQL driver with `tls=true` and the supplied Aiven CA bundle via `SSL_CERT_FILE`, which validates the server certificate and hostname. Missing or malformed PEM, unencrypted modes, and unknown query options fail closed; there is **no** `skip-verify` or SQLite fallback. Aiven's CA may rotate: update the Secret with the current/new CA bundle before rotation completes. Never include a real MySQL URI or CA private key in source, logs, or PR discussions. Connecting a new openlist version can alter existing external MySQL tables. Before openlist initialization, the existing GitHub Runner's MySQL client performs **read-only** `information_schema` checks over verified TLS: the target URI database must exist, contain no unrelated table/view names, and an existing `x_` namespace must contain the core `x_users`, `x_storages`, and `x_setting_items` tables (not views). A partial or mismatched schema fails closed before migrations or admin-password changes. This guard does **not** independently prove database ownership or that the corrected Secret points to the intended schema. No additional Database MCP connection, tool or service is required. The owner waived a separate backup prerequisite on 2026-10-24; the waiver does not authorize modifications to unexpected existing data.

**OpenList admin password recovery:** Normal `openlist.yml` Sessions never reset a persistent administrator password; they still require a successful local admin login before signed Ready. For an existing database, keep the repository Actions Secret `SESSION_SERVICE_PASSWORD` synchronized with the actual OpenList administrator password. To recover access, set the desired value in that Secret, then use **Actions → `openlist-admin-reset` → Run workflow** on `main`, entering exactly `RESET_OPENLIST_ADMIN` as confirmation. This one-time job is serialized with OpenList Sessions, reuses the same verified-TLS/MySQL schema preflight and digest-pinned image, calls the native `openlist admin set` only on explicit recovery, verifies a real admin login and removes its temporary local container/files. It refuses empty/unknown schemas, does not start a public Tunnel and never prints credentials. Wait for the maintenance job to succeed before opening a new Session. Do not trigger recovery during normal startup or merely to rotate another account's password.

The signed **Claim runs before** the pinned Tailscale Action, SSH authorization, service secrets and `ready`. An unregistered direct `workflow_dispatch` must stop at Claim; its GitHub Job failure is an expected security result, not proof that the private Session was started. The Tailscale federation needs a client ID, audience, `auth_keys` scope limited to `tag:session-actions`, and an explicit GitHub OIDC trust policy; Tailscale's own [workload identity guide](https://tailscale.com/docs/features/workload-identity-federation) describes the required identity exchange. Do not grant `tag:session-actions` access to unrelated nodes.

The three web services bind only to loopback and use SHA-256-pinned `cloudflared 2026.10.3` Quick Tunnels. chrome and code-server require `--allowed-mail` with the single validated `OWNER_EMAIL` mailbox and fail closed if it is absent, invalid or contains a wildcard; an anonymous `GET -> 302` email-OTP redirect is required for Ready, and an unauthenticated `POST -> 401` must also be checked in CI. They have no second application password. openlist deliberately omits `--allowed-mail`: anyone with its temporary public URL can reach its public pages, guest routes and shares, subject to native OpenList permissions. Its Tunnel is Ready only when an anonymous request to `/api/public/settings` returns the expected OpenList JSON; the startup separately verifies its administrator login before Ready. Do not mistake these checks for proof that private OpenList data are protected: review guest permissions, public shares and admin credentials before live activation. For chrome/code-server, each service must independently pass startup, signed Ready, anonymous GET redirect, unauthenticated POST denial, at least 60 seconds of stable availability, and shutdown/cleanup. When the launcher, validated `OWNER_EMAIL`, OTP policy, and executing revision are equivalent, one Owner-confirmed OTP login and usable GUI can validate the shared authentication path; any omitted repeat human login must be explicitly recorded as `Waived (shared-auth equivalence)`, never `Pass`. A service-specific difference or failure requires targeted additional validation. OpenList retains its public-route and native admin-login acceptance. [cloudflare/cloudflared#1752](https://github.com/cloudflare/cloudflared/issues/1752) reports that some protected Quick Tunnel sessions expire within seconds; if reproduced, do not remove `--allowed-mail` from chrome/code-server as a workaround. **Cloudflare describes Quick Tunnels as development/testing only**; they offer no production SLA. No named Tunnel, static public hostname or Tunnel Token is required.

Windows uses the existing GitHub-hosted Runner administrator account with SSH plus native RDP, while Ubuntu Linux uses its existing unprivileged Runner account (which has passwordless sudo access). Each SSH listener binds only to its Tailnet IPv4 address; Windows also restricts SSH/RDP inbound firewall rules to that adapter/address and requires RDP NLA. There is no new user or SSH authorized key for either. Passwords are accepted according to the platform's own local account policy, without a custom 16-character minimum. Because these accounts can perform privileged operations, tightly restrict Tailnet network access and protect the shared GitHub Actions Secret. Windows administrator password-authenticated SSH and RDP have now both been confirmed by the owner on real Windows-hosted Runners (latest SSH [#40109374696](https://github.com/lirtual/github-actions/actions/runs/40109374696)); authentication tests do not by themselves prove any later Session is still online. The openlist container uses ephemeral Runner-local configuration and cache while its **external MySQL database persists** beyond Session termination. Inspect database ownership and schema read-only before the first live openlist initialization. The owner waived a separate manual backup prerequisite on 2026-10-24; do not initialize or reset unexpected existing data. Runner cleanup never drops database tables. chrome and code-server temporary Runner state is discarded when the Job ends. This is not a backup service or permanent remote computer.

The Session duration is bounded to 300 minutes by the first Runner step (before checkout), while the GitHub Job uses `timeout-minutes: 360` as a separate hard safety cutoff, leaving up to 60 minutes for best-effort shutdown and cleanup. The first step is the earliest controllable time marker, not GitHub's internal pre-step scheduling timestamp. The shared stdlib-only Python helper validates and preserves that marker; it never restarts the clock. If the Job fails before Ready, the published Workflow must not claim a successful Session. Ready means the private service passed its local health check; it is not a guarantee that the requesting device can connect through Tailnet ACLs.

## Production acceptance boundaries

- Web Session access deliberately differs from the original Tailnet-only Spec: Quick Tunnel creates ephemeral public HTTPS endpoints. chrome/code-server are gated by Cloudflare email OTP and have **no second password**; openlist has no Cloudflare OTP and instead enforces native accounts/guest permissions for persistent data. OTP redirect and POST rejection are security prechecks for chrome/code-server, **not** proof of successful authenticated access. For chrome/code-server, require one Owner-confirmed OTP/GUI login on the equivalent shared-auth path and independent per-service operational and security checks as described above. Record any unperformed repeat manual GUI login as `Waived`, not `Pass`; service-specific differences require targeted testing. OpenList still requires public-route and native admin-login checks.
- A signed Ready records the temporary Quick Tunnel locator on the existing D1 Session row. Existing `workflow_status` and `workflow_result` expose `session_url` only while Ready; the URL is hidden when stopping/terminated and discarded on verified physical release. This is a connection hint, not proof of successful Cloudflare OTP or application login.
- openlist uses the configured external MySQL schema and **does persist database records after a Session ends**. Its preflight checks table shape only, not ownership or an untouched dataset; the owner must confirm the intended schema and acceptable retained test data. The Runner cleanup removes local files, not the external database. Never automatically drop or overwrite the external schema as part of Session cleanup.
- Windows live password-authenticated RDP and SSH have now both been accepted by the owner; the GitHub-hosted Runner's minimum-8-character policy remains scoped to disposable Windows Runners. Future Runs must still pass actual setup, signed Ready, and physical cleanup checks; OIDC Claim/Tailscale alone is not proof of access.
- The existing CI now runs for relevant default-branch changes as well as pull requests. A passing isolated CI does not replace authorized full production access acceptance.
