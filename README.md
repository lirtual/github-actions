# Session Actions

Temporary, repository-related development and test sessions executed on GitHub-hosted runners through the approved Workflow MCP action protocol.

Implementation is tracked by [Spec #1](https://github.com/lirtual/session-actions/issues/1). GitHub workflow discovery is not execution authorization; no session should be dispatched without a published and approved Workflow MCP plan.

## Native Task acceptance

`.github/workflows/verify-action.yml` is a minimal **Task** for validating the approved Workflow MCP lifecycle (not a persistent Session or general-purpose shell). It declares all three required server-owned identity inputs; only the bounded `outcome` choice is caller-selectable.

Before an owner-approved live acceptance, the repository owner must configure these **non-secret Actions variables** with the already-approved Workflow MCP endpoint and audience:

- `WORKFLOW_ACTION_CLAIM_URL` — the HTTPS Worker origin ending in `/github/action/claim`
- `WORKFLOW_ACTION_OIDC_AUDIENCE` — exactly the server's `GITHUB_ACTION_OIDC_AUDIENCE`

The action retries only temporary signed Claim HTTP 503 responses with fresh OIDC tokens, accepts a signed `already_claimed` replay after a lost HTTP receipt, and permanently rejects HTTP 403. It fails closed if either variable, a valid GitHub-issued OIDC token, or the D1 Attempt claim is unavailable. It never reads application secrets or joins Tailscale.

Live `workflow_dispatch` requires the workflow definition on GitHub's **default branch** and an owner-reviewed, SHA-bound Git tag. An approved Task on protected `v0.1.1` actually completed [GitHub Run #40056368526](https://github.com/lirtual/session-actions/actions/runs/40056368526) with signed Claim and successful Workflow MCP terminal reconciliation; CI alone would not prove this.

## Download Task (Spec #51)

The bounded `.github/workflows/download.yml` Task uses aria2 and a fixed rclone Remote for repository-related public HTTP(S) artifacts. The Owner-approved production `download` Workflow is **active** for authenticated manual Runs only (no Cron/Webhook), pinned to immutable `v0.1.42-rc.6` / `45c61731f4d95e73471405834d91d3815d7f2338` (Azure WireServer egress hardening, [PR #67](https://github.com/lirtual/session-actions/pull/67)). Discovery and CI success alone never authorize direct Task dispatch; each execution still requires a valid Workflow MCP OIDC Claim.

The existing GitHub **Environment `download`** uses these settings (verify them before any future storage change):

- **Secret `DOWNLOAD_RCLONE_CONFIG_B64`**: Base64-encoded `rclone.conf`; never print the plaintext configuration or commit it.
- **Variable `DOWNLOAD_REMOTE_NAME`**: the single approved rclone Remote name; currently `koofr`.
- **Variable `DOWNLOAD_REMOTE_BASE_DIR`**: an **explicit, already existing** relative directory inside that Remote; currently case-sensitive `Downloads`. Missing, invalid, differently cased or nonexistent directories are rejected; there is no implicit fallback to the cloud root.

The Owner controls the destination root, and the Task caller cannot override it.
**Next release candidate (local changes, not yet deployed):** a URL-only batch
writes directly to `<remote>:<base>/<downloaded-filename>` (currently
`koofr:Downloads/<downloaded-filename>`), without any `run-...` directory.
The existing optional validated `destination_dir` remains available for
explicit relative subdirectories. Each batch checks all target paths and
case-insensitive aliases before the first upload, rejects existing objects,
uses rclone `--immutable` and independently reads back SHA-256. There is no
cloud-provider atomic create-only guarantee: another writer can still race
between existence checks and writes. A conflict fails, never silently replaces
an already-discovered file. Partial/unknown uploads remain non-success and are
never automatically replayed or deleted.

The **currently published** `rc.6` Workflow still creates isolated random
Task roots until a new immutable release and a separately authorized production
publication occur. The old `rc.5` production Koofr E2E and `rc.6` network
regression evidence remain valid for those exact revisions only. Production
uses manual, authenticated runs with single-element `download_batches` where
the one JSON batch may contain multiple public HTTP(S) URLs. The existing
Q13 public-HTTPS egress guarantee, Q15 non-atomic write residual risk,
Owner-waived live mid-upload fault injection, and Q34 optional signed success
receipt remain unchanged.

## Five native Session Actions

Each workflow lives in its own file and uses GitHub OIDC → Workflow MCP Claim → access setup → verified Ready → bounded hold → cleanup. Only the ubuntu and windows Sessions join the private Tailnet. The web Sessions use Cloudflare Quick Tunnels without a Tailscale dependency: chrome and code-server require Cloudflare email OTP, while openlist is public at the Tunnel layer and uses its own login and guest permissions:

| Workflow | GitHub-hosted runner | Private access | Local service |
| --- | --- | --- | --- |
| `ubuntu.yml` | Ubuntu | Password SSH as the existing `runner` account, bound to Tailscale IPv4 | Minimal command-line development |
| `windows.yml` | Windows | SSH and RDP as the existing Runner administrator, over private Tailscale | PowerShell, files and remote desktop (live RDP acceptance pending) |
| `chrome.yml` | Ubuntu | Email-OTP protected Quick Tunnel HTTPS | chrome GUI bound to `127.0.0.1:3000`; no separate login |
| `code-server.yml` | Ubuntu | Email-OTP protected Quick Tunnel HTTPS | code-server `4.140.0`, `--auth none`, bound to `127.0.0.1:8080` |
| `openlist.yml` | Ubuntu | Cloudflare Quick Tunnel HTTPS | openlist Docker `v4.2.6` with native `admin` password on `127.0.0.1:5244` |

**How to find your Session:** For ubuntu and windows, the default `session_mode: fixed` requests exactly `session-ubuntu` or `session-windows`; both use GitHub-hosted `ubuntu-latest` / `windows-latest` runners. Explicitly select `session_mode: temporary` for an independent `sa-<github_run_id>-a<github_run_attempt>` Tailnet hostname. A fixed hostname is **not** a permanent VM: each fixed Session still has the same bounded lifetime and cleanup. Workflow MCP atomically limits each fixed Action to one active physical Session (starting, ready, stopping and uncertain all count) within the existing four global slots. A second fixed start does not dispatch another GitHub Job: the failed start provides the existing Session Run ID for lookup. Only verified physical termination releases the fixed slot. Tailscale's existing GitHub Action Post step logs out its ephemeral node when the Job finishes; if an old device has not released its name and Tailscale allocates a suffixed name, startup fails before Ready rather than exposing a misleading locator. After the signed Ready state, `workflow_status` exposes `private_hostname` (for example `sa-123456789-a1`) and still reports `physical_health: unverified` until physical state reconciliation. These names work only within an authorized tailnet with correct MagicDNS/Tailscale SSH access rules. For ubuntu use `ssh runner@<private_hostname>`; for windows use `ssh runneradmin@<private_hostname>` (the actual account is detected from each Runner). Both use the same SSH password from `SESSION_SYSTEM_PASSWORD`. Windows also supports RDP on Tailscale TCP/3389 using `runneradmin` and the same underlying Windows account password. The disposable GitHub-hosted Windows Runner enforces **only a minimum of 8 characters** for this local account password; no fixed uppercase/lowercase/number/symbol combination is required. This local policy adjustment is refused on self-hosted Runners, and the SSH/RDP network remains Tailnet-restricted. Windows SSH and RDP authenticate the same existing local account and automatically share `SESSION_SYSTEM_PASSWORD`; no RDP-specific Secret is needed. For chrome, code-server and openlist, the signed Ready request records a temporary HTTPS URL on `trycloudflare.com`, exposed as `session_url` through existing Workflow MCP `workflow_status` / `workflow_result` only while the Session is Ready. GitHub Job Summary and the one-day `session-tunnel-url` artifact remain fallbacks. For chrome and code-server, the email one-time PIN is the **only** login gate; the services listen on loopback only and cannot be exposed unless the protected Tunnel's anonymous redirect is verified. openlist still requires its native administrator login to preserve its database-backed privileges. The temporary `trycloudflare.com` URL is a public Internet endpoint without an availability guarantee. chrome and code-server require Cloudflare email OTP before access; openlist allows anonymous HTTP requests and enforces its own user and guest permissions.

**RDP → UU handoff:** An ordinary RDP client close can leave the Windows desktop locked and unusable from UU Lite. On the real `v0.1.28` disposable Runner, the owner verified that `tscon <active RDP session ID> /dest:console` safely returned the session to an unlocked, UU-controllable desktop. The Windows Action now registers an account-scoped Windows `RemoteDisconnect` scheduled task to attempt the same handoff automatically after a normal RDP disconnect, selecting exactly one disconnected Runner-user session dynamically. It does not disable Windows locking, bypass the lock screen or install a resident service. The task is removed during Session cleanup, and registration is refused outside GitHub-hosted Windows Runners. **Automatic event-triggered handoff is a candidate until a real RDP-close → UU-interactive acceptance succeeds; manual `tscon` acceptance alone does not prove it.**

**UU Lite invite link (optional):** The disposable Windows Runner tries UU Lite's native **复制并分享** button once on initial startup and only accepts a strict `https://uuyc.163.com/invite/<32 hex chars>` URL. This link grants remote-control access and is protected exactly like the device ID and verification code. It is stored only in the existing account-private `uu-remote.json` as optional `share_url` and forwarded, when present, in the existing encrypted `uu.credentials` observation. It is never added to Status/Result/Job Summary/logs/Artifacts. The owner's clipboard is restored when safe; refreshes never click the button or modify the clipboard, retain the link only while the device ID and code are unchanged, and omit it otherwise. If the button or clipboard is unavailable, the existing ID and code continue working. CI verifies parsing and compatibility; a real invite URL requires separate private Windows/UI acceptance.

**Optional UU Lite on Windows (candidate, pending phone acceptance):** The Windows Session attempts to start NetEase's officially signed, account-free UU Remote Lite alongside its existing SSH/RDP; failure to start UU does not change SSH/RDP readiness. UU device ID and current verification code are read only inside the interactive Runner session, not logged or published as artifacts. If capture succeeds, use the existing Tailscale-only SSH access to `runneradmin`, then run `powershell -NoProfile -Command "Get-Content -Raw (Join-Path $env:LOCALAPPDATA 'session-actions\uu-remote.json')"` **inside the remote shell** to retrieve the short-lived details. The existing Windows Session hold loop re-reads the current UU Lite UI verification code approximately every 30 seconds and atomically updates this file when it changes. Spec #288 also reports each validated observation (including an unchanged code or an explicit unavailable sample) to Workflow MCP through a signed GitHub OIDC endpoint. After the separately reviewed Worker migration, Secret, and two-repository release, an authenticated single-owner MCP client can explicitly call `workflow_session_data_get(run_id, step_id, key='uu.credentials')`; the result is limited by the 90-second Server TTL, active Session and live GitHub Run gates. Never expose this value through status/result, logs, GitHub Summary, or Artifacts; an explicitly requested MCP response becomes part of the ChatGPT conversation. This does not replace local account-only storage or authorize access for clients without the existing owner Bearer token. **Read the file again for each new connection; do not reuse a copied code from the previous remote session.** Refresh also checks UU-owned tray-hidden windows, rather than relying only on `Process.MainWindowHandle`. The private JSON has `status: ready` with current ID/code when verified; if the UI is inaccessible, it instead contains `status: unavailable` and a non-secret `reason` (such as `process_missing`, `window_unavailable`, `code_unavailable` or `code_unstable`) and **no** ID/code. The existing hold retries on the next cycle; SSH/RDP remain available. A locked Windows secure desktop may still make UU's own UI inaccessible; actual post-lock reconnection is not guaranteed until accepted on a live Session. The file is readable only by the Runner account, and is removed on normal cleanup; the VM is discarded after its Session. Never paste these values into public GitHub logs or issue comments. A valid file establishes only locally captured candidate credentials; mobile connection, RDP session handoff, reconnect behavior, and lock-screen operation still require independent live acceptance. This is not a persistent UU device or a substitute for a private access policy.


**Supply-chain bounds:** the code-server 4.140.0 linux-amd64 download is checked against hardcoded SHA-256 `864c5d01c808ade57e4d12c708717be7a187219fded60428f263b9e2da9f6b48` (matched two distinct GitHub-hosted Runner downloads). openlist v4.2.6 is pinned to multi-architecture image index digest `sha256:c555c6e1c8af2aead38ed12ec761ac077fdf046d19cf033414be8e056aec6b64`. Any new release must be reviewed and update these immutable values explicitly; the version/tag alone is not authority.

The three internal workflow_dispatch inputs `attempt_id`, `dispatch_id`, `capability_id` are supplied **only** by Workflow MCP. Users may choose `duration_minutes` (1–300, default 300). These workflows do not accept shell commands or arbitrary URLs as input.

**Optional per-Run duration (preferred for newly published Workflow MCP plans):** All five Session Action YAMLs default to **300** minutes and the Runner strictly enforces **1–300** whole minutes. The Workflow engine can opt in once by declaring top-level `inputs.duration_minutes: 300` and setting the reviewed Action input to `duration_minutes: {ref: inputs.duration_minutes}` with `duration_mode: explicit`. Subsequent starts with no duration use 300, and starts with `workflow_run.inputs.duration_minutes` use the supplied 1–300 value **without republishing**. The exact reviewed GitHub tag and inputs other than duration remain immutable; the published Plan must explicitly opt in. Existing pinned `duration_mode: repository` workflows continue to work without changing their behavior until deliberately republished. The 360-minute job timeout is a separate emergency cleanup backstop, not the user-selectable Session maximum.

**Repository-managed formal Session duration:** Set the non-secret GitHub Actions repository variable `SESSION_DURATION_MINUTES` to `300` under **Settings → Secrets and variables → Actions → Variables**. Formal Published Workflow MCP Plans explicitly pin `duration_mode: repository` and a `duration_minutes: 300` fallback. Their *next* GitHub Jobs use the repository variable (1–300 whole minutes); changing the variable affects only new jobs, not active Sessions, and does not require republishing the formal Plan. If the variable is absent, these Plans use 300. If it is present but invalid or out of bounds, the first Runner step fails before Claim and service/Tailnet startup; it does not silently fall back or extend the lifetime. Tests and one-off approved Plans use the default `duration_mode: explicit` and their pinned `duration_minutes`, ignoring the repository variable. The source ref and choice of mode remain pinned by the reviewed Published Plan; a mutable repository variable only controls the bounded runtime duration of a new opted-in Session. GitHub Job `timeout-minutes: 360` and the 300-minute hard maximum still apply.

**Repository configuration before any separately approved live acceptance:**

- Actions variables: `WORKFLOW_ACTION_CLAIM_URL` (HTTPS, exactly ending `/github/action/claim`) and `WORKFLOW_ACTION_OIDC_AUDIENCE` (exact server-owned Action OIDC audience).
- Actions variables: `TS_OAUTH_CLIENT_ID` (Tailscale workload identity client ID), `TS_AUDIENCE` (Tailscale OIDC federation audience). These are non-secret identifiers; Tailscale identity binding and tag authorization are enforced by the Tailnet trust policy.
- GitHub Actions **Variable**: `SESSION_TUNNEL_ALLOWED_EMAIL` must be exactly one mailbox that you can receive email at. The chrome and code-server workflows fail closed if it is missing or invalid; openlist does not use this variable. Set it under repository Settings → Secrets and variables → Actions → Variables; do not add a wildcard email domain. This is an **additional login gate**, not an extra service password.
- Actions secrets: `SESSION_SYSTEM_PASSWORD` (windows and ubuntu SSH), `SESSION_SERVICE_PASSWORD` (openlist administrator login only), and `OPENLIST_DATABASE_URI` (Aiven-compatible MySQL connection URI), and `OPENLIST_DATABASE_CA` (Aiven project CA certificate PEM or rotation bundle; required for verified TLS). Values must be non-empty, single-line and accepted by their application or OS. Do not paste passwords into Workflow YAML or logs. Retire `SESSION_SSH_PUBLIC_KEY`, `SESSION_SSH_PASSWORD`, `SESSION_RDP_PASSWORD`, intermediate `WINDOWS_ADMIN_PASSWORD` and obsolete `OPENLIST_ADMIN_PASSWORD` only after approved rollout.
- Tailnet: configure a narrowly scoped `tag:session-actions`, an appropriate GitHub workload identity trust policy and ACL grants. The windows and ubuntu Sessions use ordinary OpenSSH restricted to Tailnet TCP/22 and therefore rely on Tailscale **network grants**; Windows RDP on TCP/3389 is likewise restricted to Tailnet access. chrome, code-server and openlist use HTTPS Cloudflare Quick Tunnels, **not** Tailscale SSH, and must not be considered Tailnet-private. The tag does not itself grant access to unrelated nodes.
- Workflow MCP: the signed Claim and Ready endpoints, GitHub Git ref/commit approval, physical Run identity, D1 migrations, four active slots, expiry monitoring and cancellation must be deployed and verified separately.

**openlist external MySQL URI and CA:** Configure both `OPENLIST_DATABASE_URI` and `OPENLIST_DATABASE_CA` as GitHub Actions **Secrets**. Use `mysql://USER:PASSWORD@HOST:PORT/DATABASE?ssl-mode=REQUIRED` (percent-encode reserved characters in credentials). The database name is taken from the URI path; use a dedicated MySQL database/account with the intended table prefix `x_`. The parser accepts `REQUIRED` and `VERIFY_IDENTITY` and **strengthens both to verified TLS** by configuring the Go MySQL driver with `tls=true` and the supplied Aiven CA bundle via `SSL_CERT_FILE`, which validates the server certificate and hostname. Missing or malformed PEM, unencrypted modes, and unknown query options fail closed; there is **no** `skip-verify` or SQLite fallback. Aiven's CA may rotate: update the Secret with the current/new CA bundle before rotation completes. Never include a real MySQL URI or CA private key in source, logs, or PR discussions. Connecting a new openlist version can alter existing external MySQL tables. Before openlist initialization, the existing GitHub Runner's MySQL client performs **read-only** `information_schema` checks over verified TLS: the target URI database must exist, contain no unrelated table/view names, and an existing `x_` namespace must contain the core `x_users`, `x_storages`, and `x_setting_items` tables (not views). A partial or mismatched schema fails closed before migrations or admin-password changes. This guard does **not** independently prove database ownership or that the corrected Secret points to the intended schema. No additional Database MCP connection, tool or service is required. The owner waived a separate backup prerequisite on 2026-10-24; the waiver does not authorize modifications to unexpected existing data.

**OpenList admin password recovery:** Normal `openlist.yml` Sessions never reset a persistent administrator password; they still require a successful local admin login before signed Ready. For an existing database, keep the repository Actions Secret `SESSION_SERVICE_PASSWORD` synchronized with the actual OpenList administrator password. To recover access, set the desired value in that Secret, then use **Actions → `openlist-admin-reset` → Run workflow** on `main`, entering exactly `RESET_OPENLIST_ADMIN` as confirmation. This one-time job is serialized with OpenList Sessions, reuses the same verified-TLS/MySQL schema preflight and digest-pinned image, calls the native `openlist admin set` only on explicit recovery, verifies a real admin login and removes its temporary local container/files. It refuses empty/unknown schemas, does not start a public Tunnel and never prints credentials. Wait for the maintenance job to succeed before opening a new Session. Do not trigger recovery during normal startup or merely to rotate another account's password.

The signed **Claim runs before** the pinned Tailscale Action, SSH authorization, service secrets and `ready`. An unregistered direct `workflow_dispatch` must stop at Claim; its GitHub Job failure is an expected security result, not proof that the private Session was started. The Tailscale federation needs a client ID, audience, `auth_keys` scope limited to `tag:session-actions`, and an explicit GitHub OIDC trust policy; Tailscale's own [workload identity guide](https://tailscale.com/docs/features/workload-identity-federation) describes the required identity exchange. Do not grant `tag:session-actions` access to unrelated nodes.

The three web services bind only to loopback and use SHA-256-pinned `cloudflared 2026.10.3` Quick Tunnels. chrome and code-server require `--allowed-mail` with the `SESSION_TUNNEL_ALLOWED_EMAIL` mailbox and fail closed without it; an anonymous `GET -> 302` email-OTP redirect is required for Ready, and an unauthenticated `POST -> 401` must also be checked in CI. They have no second application password. openlist deliberately omits `--allowed-mail`: anyone with its temporary public URL can reach its public pages, guest routes and shares, subject to native OpenList permissions. Its Tunnel is Ready only when an anonymous request to `/api/public/settings` returns the expected OpenList JSON; the startup separately verifies its administrator login before Ready. Do not mistake these checks for proof that private OpenList data are protected: review guest permissions, public shares and admin credentials before live activation. Final positive access acceptance requires real OTP login and usable GUI for chrome/code-server, or actual anonymous/public-page and native-admin-login checks for openlist, with stable access for at least 60 seconds. [cloudflare/cloudflared#1752](https://github.com/cloudflare/cloudflared/issues/1752) reports that some protected Quick Tunnel sessions expire within seconds; if reproduced, do not remove `--allowed-mail` from chrome/code-server as a workaround. **Cloudflare describes Quick Tunnels as development/testing only**; they offer no production SLA. No named Tunnel, static public hostname or Tunnel Token is required.

Windows uses the existing GitHub-hosted Runner administrator account with SSH plus native RDP, while Ubuntu Linux uses its existing unprivileged Runner account (which has passwordless sudo access). Each SSH listener binds only to its Tailnet IPv4 address; Windows also restricts SSH/RDP inbound firewall rules to that adapter/address and requires RDP NLA. There is no new user or SSH authorized key for either. Passwords are accepted according to the platform's own local account policy, without a custom 16-character minimum. Because these accounts can perform privileged operations, tightly restrict Tailnet network access and protect the shared GitHub Actions Secret. Windows administrator password-authenticated SSH and RDP have now both been confirmed by the owner on real Windows-hosted Runners (latest SSH [#40109374696](https://github.com/lirtual/session-actions/actions/runs/40109374696)); authentication tests do not by themselves prove any later Session is still online. The openlist container uses ephemeral Runner-local configuration and cache while its **external MySQL database persists** beyond Session termination. Inspect database ownership and schema read-only before the first live openlist initialization. The owner waived a separate manual backup prerequisite on 2026-10-24; do not initialize or reset unexpected existing data. Runner cleanup never drops database tables. chrome and code-server temporary Runner state is discarded when the Job ends. This is not a backup service or permanent remote computer.

The Session duration is bounded to 300 minutes by the first Runner step (before checkout), while the GitHub Job uses `timeout-minutes: 360` as a separate hard safety cutoff, leaving up to 60 minutes for best-effort shutdown and cleanup. The first step is the earliest controllable time marker, not GitHub's internal pre-step scheduling timestamp. The shared stdlib-only Python helper validates and preserves that marker; it never restarts the clock. If the Job fails before Ready, the published Workflow must not claim a successful Session. Ready means the private service passed its local health check; it is not a guarantee that the requesting device can connect through Tailnet ACLs.

### Acceptance and publication gate

The five independent Sessions have been exercised through **published and approved** Workflow MCP plans and actual GitHub-hosted runners. ubuntu [#40057129644](https://github.com/lirtual/session-actions/actions/runs/40057129644) completed signed Claim/Ready, **the previous Tailscale SSH authentication**, command execution, cancellation and quota release. That prior run does **not** validate the new password-authenticated OpenSSH implementation. chrome [#40057287818](https://github.com/lirtual/session-actions/actions/runs/40057287818), code-server [#40057289722](https://github.com/lirtual/session-actions/actions/runs/40057289722) and openlist [#40057291691](https://github.com/lirtual/session-actions/actions/runs/40057291691) previously returned signed Ready using SSH port forwarding and loopback HTTP responses; **those runs do not validate the new Tunnel/native-password access path**, which requires its own acceptance. A four-Session concurrency test denied a fifth attempt without dispatch. Windows [#40060922399](https://github.com/lirtual/session-actions/actions/runs/40060922399) on protected `v0.1.13` passed OIDC Claim, Tailnet and **the previous non-admin ED25519 SSH scheme** (`WIN_FINAL_PASS`, exit 0), then physically terminated and released its slot. This historic evidence does **not** validate the new administrator password-login scheme, which requires separate live approval and access testing. In each case, signed Ready was correctly distinguished from external Job completion.

PR CI checks Actionlint, shared protocol and OIDC Claim failure tests, native Windows prerequisites and actual loopback-bound chrome, code-server and openlist service startup. openlist's local startup now additionally requires a successful admin login with the configured ephemeral password **before** signed Ready; the CI smoke uses only a temporary CI password. A prior live openlist Session on protected `v0.1.14` [#40062276499](https://github.com/lirtual/session-actions/actions/runs/40062276499) confirmed the startup script's `openlist admin login validated` message, signed Ready, authenticated Tailscale SSH access and HTTP 200; normal cancellation reconciled to physical `cancelled`, external `terminated`, and 0 active slots. The `v0.1.14` evidence here is historical. Current reviewed published versions use `v0.1.21` for chrome/code-server, `v0.1.20` for Windows, and `v0.1.19` for ubuntu/openlist; current physical health must be checked per Run. A separate one-minute **natural-expiration** Linux Session [#40062561451](https://github.com/lirtual/session-actions/actions/runs/40062561451) finished its own bounded hold and GitHub Job with `success` (not user cancellation), then the Worker reconciled the external Session to `terminated` / Attempt `succeeded` and restored the active slot count to zero. Broader negative/fault-injection cases are covered in `lirtual/mcp-workers/apps/workflow-mcp-worker/tests/github-action-{oidc,session,orchestration,review,inputs,run-state}.test.ts`, including wrong identities and Git refs, duplicated/lost callbacks, uncertain GitHub responses and no premature quota release. Those are **automated tests**, not live adversarial production experiments. A continuous 300-minute wall-clock run has not been executed; the workflow's 360-minute hard limit, 300-minute duration input bounds and short-lived expiration behavior are distinct controls.

Release and acceptance are separate gates. Keep production D1 changes owner-executed, and never bypass the Worker release check for an unresolved or indeterminate Run. Before activating a Session, configure the approved GitHub identity and required credentials. ubuntu and windows additionally require the narrow Tailscale tag/SSH policy. Web Sessions use Quick Tunnels: chrome/code-server require Cloudflare email OTP as their sole login, while openlist uses a public Tunnel with native login/guest permissions. Never expose local origins directly or disable the chrome/code-server OTP gate as a workaround.


**Action naming and release boundary:** The Session Action identifiers are `ubuntu`, `windows`, `chrome`, `code-server` and `openlist`. The former `linux.yml` / `linux-ssh.sh` names are retired. Renaming a GitHub Workflow changes its GitHub workflow identity: existing published Workflow MCP plans pinned to the retired file/Workflow ID are **not automatically migrated**. Before executing the renamed `ubuntu` Action, release an owner-reviewed immutable Git tag containing `ubuntu.yml`, check the newly discovered workflow ID and contract, and explicitly publish a new approved Workflow MCP plan. Do not reuse the previous `linux.yml` approval or assume the old published Workflow remains dispatchable.

## Production acceptance boundaries

- Web Session access deliberately differs from the original Tailnet-only Spec: Quick Tunnel creates ephemeral public HTTPS endpoints. chrome/code-server are gated by Cloudflare email OTP and have **no second password**; openlist has no Cloudflare OTP and instead enforces native accounts/guest permissions for persistent data. OTP redirect and POST rejection are security prechecks for chrome/code-server, **not** proof of successful authenticated access. Do not claim positive acceptance without a real owner OTP login and GUI for chrome/code-server, or public route plus native OpenList admin-login checks.
- A signed Ready records the temporary Quick Tunnel locator on the existing D1 Session row. Existing `workflow_status` and `workflow_result` expose `session_url` only while Ready; the URL is hidden when stopping/terminated and discarded on verified physical release. This is a connection hint, not proof of successful Cloudflare OTP or application login.
- openlist uses the configured external MySQL schema and **does persist database records after a Session ends**. Its preflight checks table shape only, not ownership or an untouched dataset; the owner must confirm the intended schema and acceptable retained test data. The Runner cleanup removes local files, not the external database. Never automatically drop or overwrite the external schema as part of Session cleanup.
- Windows live password-authenticated RDP and SSH have now both been accepted by the owner; the GitHub-hosted Runner's minimum-8-character policy remains scoped to disposable Windows Runners. Future Runs must still pass actual setup, signed Ready, and physical cleanup checks; OIDC Claim/Tailscale alone is not proof of access.
- The existing CI now runs for relevant default-branch changes as well as pull requests. A passing isolated CI does not replace authorized full production access acceptance.
